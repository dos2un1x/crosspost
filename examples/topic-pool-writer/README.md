# 候选池写入器 · 参考实现（实现在引擎，项目侧只转发）

> **这个参考实现与前两个相反：通用实现在引擎里，项目侧只做接线。**
> 候选池 `topic-pool.json` 有**两个写入者**——引擎自己（回填 `articleId`、Console 的删除）
> 与项目侧的候选入库——所以"行形状、合并规则、写锁"只能有一处实现。项目侧的写入器
> 因此退化成一层薄转发：解析参数 → 找引擎 → 调 `topicPoolUpsert` → 透传退出码。
>
> 契约（字段表 + 两条纪律）：[`../../docs/writing-pipelines.md`](../../docs/writing-pipelines.md) §8。

## 先看你在哪一面

| 调用方                                   | 用什么                                                                                                                     | 为什么                                                                                          |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **AI 会话**（写作/一键生成链路里的模型） | MCP 工具 `topic_pool_upsert`（`{date, slot, rows:[{keyword,title,score,status,reason,articleId?}], manual?, articleId?}`） | 字段形状写进工具 schema：漏 `title`、`status` 给错字在**工具调用**就被挡住；也不经过 shell 引号 |
| **脚本 / 定时链路 / 维护**               | 下面的 CLI（或本目录的转发器）                                                                                             | 没有会话上下文，直接一条命令；退出码即结论                                                      |

两条路是同一个 handler、同一份实现（`src/topic-pool.mjs`），不会分叉。

## 引擎侧的三条命令

| 命令                                                                                                                                 | 作用                                           | 退出码                                                   |
| ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------- | -------------------------------------------------------- |
| `node <引擎>/crosspost-runtime/src/cli.mjs topicPoolUpsert --date=… --slot=… --json='[[…]]' [--manual] [--article-id=…] [--dry-run]` | 写入候选（**唯一写入口**）                     | `0` 成功／`1` 被拒（形状不对、条目数会减少、选不出项目） |
| `… topicPoolValidate --json='[[…]]'`                                                                                                 | 只校验行形状，不碰磁盘                         | 同上（`0` 合法／`1` 有问题）                             |
| `… topicPoolShow`                                                                                                                    | 只读：路径 + 各状态计数 + 最近一天各 slot 条数 | `0`（文件缺失也返回 `existed:false`，不算错）            |

目标项目按这个顺序解析，**说不清就报错，绝不猜**：`--pool=<file>` → `--project=<id>` →
`cwd` 落在某个已登记项目根里 → 本机只有一个合法项目 → 报错并列出可选项目。
定时链路（launchd / cron）没有 cwd 上下文，用 `--project=<id>` 最稳。

**退出码就是结论**：被拒时 CLI 打印
`{"error":"拒绝写入（本次一个字节都没落盘）：…"}` 并以 `1` 退出。项目侧脚本必须把这个
退出码透传出去，让那一轮**响亮失败**——不要 `|| true`，更不要"引擎不在就自己写一遍"。

## 两个可直接复制的转发器

- [`upsert.sh`](upsert.sh) —— bash（定时脚本里用）
- [`topic_pool_upsert.py`](topic_pool_upsert.py) —— Python，保留
  `--date/--slot/--json/--manual/--article-id/--pool` 这套参数形状

两者都只做三件事：找引擎（`CROSSPOST_ENGINE_REPO`）、转发、原样透传退出码；
**找不到引擎就 `exit 1`**，不给自己留一条"悄悄自己写"的后路。

## 行形状

每行 `[keyword, title, score, status, reason, articleId?]`：

- `keyword` 非空字符串；与 `date` + `slot` 一起构成唯一键
- `title` 字符串（可为空串）或 `null`——**不能省略**：按位置取字段时少给一个，
  后面所有字段会整体左移（分数进 `title`、原因进 `status`），而这类数据在 Console 上
  看着只是"有点怪"，统计却已经错了
- `score` 0–100 的数字或 `null`；`status` ∈ `adopted` / `generated` / `rejected`；
  `reason` 字符串（可空串）；`articleId` 字符串或省略

一次调用里的任何一行不合格，**整次写入都会被拒绝**（一个字节都不落盘）——这是刻意的：
候选池是"这一轮的结论"，写一半比不写更难收拾。

## 合并规则（引擎负责，项目侧不用管）

按 `(date, slot, keyword)` upsert：命中就地更新，未命中追加（`id` = `<date>-<slot>-<NN>`，
`--manual` 用 `manual-NN`）；**绝不移除**同日同 slot 的其它条目；已 `generated` 的条目不降级；
`articleId` 只增不清；`reason` 追加而不是覆盖。

## 为什么不让项目侧自己写文件

写入不只是一个 `writeFile`：它要拿锁（与引擎的回填互斥）、要原子写 + 回读、
要在"少给字段"这类形状错误上当场拒绝。这些规则散成两份实现时，任何一份漏掉一条，
症状都出现在**别处**（Console 渲染、引擎统计、甚至"这条为什么没入库"）。
把实现留在引擎，项目侧换语言、换调度方式都不影响契约。
